# Chapter 03: METHODOLOGY

This study adopted an experimental approach to investigate concurrency control in multi-agent workflows that access shared resources through the Model Context Protocol (MCP). The research focused on a specific problem: an agent may produce a decision from a resource snapshot that becomes outdated before the agent commits its update. Conventional optimistic concurrency control (OCC) detects the version mismatch, but restarting the affected agent from the beginning can discard work that remains useful. The proposed dependency-aware OCC approach combines version validation, semantic conflict classification and selective recovery to determine which work can be reused.

A research prototype was developed and evaluated against three baseline protocols: unprotected execution, application-level pessimistic locking and OCC with a full restart of the conflicting worker. The evaluation measured final-state correctness, execution time, token consumption, discarded computation and recovery activity. Data were generated through controlled experiments rather than collected from human participants or an external observational dataset.

## 3.1. DATA COLLECTION

### 3.1.1. Experimental data and shared-resource structure

The experimental dataset consisted of execution records produced by two workers, identified as Worker A and Worker B. Each execution used an isolated shared resource containing three application fields: `quantity`, `price` and `description`. The resource also had a unique identifier and an integer version. Resources were initialized at version 1, and each successful update increased the version by one.

Workers received natural-language tasks that either assigned a fixed value or required a decision based on the current resource state. A fixed price assignment could remain valid after another worker changed an unrelated description. In contrast, an allocation calculated from the current quantity could become invalid after another worker changed that quantity. This distinction enabled the evaluation of structural conflicts and semantic disruption separately.

### 3.1.2. Scenario design and ground truth

The project separated development validation scenarios from a held-out evaluation set. The held-out set contained ten manually specified scenarios: five non-disruptive and five disruptive. Non-disruptive scenarios involved independent fixed assignments to different fields. Disruptive scenarios involved arithmetic dependencies or conditions whose validity changed after Worker B's update.

Each scenario specified the initial resource, the two worker tasks, a semantic ground-truth label and an expected final resource. The expected final state represented the prescribed order in which B's task was applied before A evaluated the resulting state. This order was especially important for non-commutative operations. For example, if B set a price to 21 and A then reduced the current price by 8, the expected final price was 13.

The ground-truth labels and expected results were explicit scenario specifications. They were not generated by the Semantic Auditor. The auditor received task and state evidence, while its prediction was evaluated separately against the stored ground truth. The dataset therefore provided two distinct outcomes: classification quality and application-level correctness.

### 3.1.3. Repeated execution and scheduling

The available final benchmark contained ten repetitions of every scenario under each of four protocols. The resulting dataset size was:

`10 scenarios × 4 protocols × 10 repetitions = 400 executions.`

Each protocol contributed 100 executions, divided equally between disruptive and non-disruptive scenarios. The benchmark runner randomizes scenario order within each repetition and protocol order within each scenario using a fixed pseudorandom seed. The held-out entry point specifies seed 20261103. This describes the source configuration; the CSV export itself does not retain the seed used to launch the recorded benchmark.

For naive execution and both optimistic protocols, the runner deliberately made both workers read the initial version, allowed both to decide, committed B first and then attempted A's stale update. This controlled schedule ensured that each protocol encountered the same type of conflict. For the pessimistic baseline, B acquired the resource lock first and A waited before accessing the updated resource. Randomized experiment order reduced systematic ordering effects across trials, while the controlled within-trial schedule made the concurrency problem reproducible.

### 3.1.4. Execution isolation and provenance

Every execution used a unique resource key containing its benchmark and run identifiers. Resource initialization and response checks helped prevent one trial from reading another trial's resource. The runner also independently checked the persisted final value before recording correctness.

The trusted runtime attached run, agent and node identifiers to MCP requests through research trace headers. These identifiers were supplied by the client infrastructure rather than generated by the language model. The middleware recorded resource access, read versions, successful writes and conflicts. Read dependencies connected an execution node with the resource version that it consumed. These records supported diagnosis of stale decisions and the project's dependency analysis.

## 3.2. DATA PREPROCESSING

### 3.2.1. Selection and integrity checks

The analysis used the existing benchmark export associated with benchmark identifier `a135dae7-cd1a-4c61-b57f-eb37beb95ae0`. Results from other benchmarks and frontend demonstrations were excluded. Before aggregation, the records were checked for completeness, duplicate protocol-scenario-repetition combinations, missing error information and consistency between input, output and total token counts.

The expected experimental structure was four protocols, ten scenarios and ten repetitions. Unique run and resource identifiers were checked to confirm that all 400 execution records referred to separate trials. Final values were interpreted as structured resource objects and compared with the scenario definitions when reviewing correctness.

### 3.2.2. Data types and missing values

Latency, token counts, conflict counts, retry counts, lock wait and node counts were treated as numerical variables. Correctness was interpreted as a Boolean outcome. Scenario identifiers, protocol names and semantic labels were retained as categorical variables.

The project's summary script converts numerical columns to numeric values and replaces conversion failures with zero. It also replaces missing correctness values with false. Because these choices could affect analysis if malformed records were present, the exported dataset was checked before relying on its summaries. No input-plus-output token inconsistency was found in the available records.

Missing semantic predictions for the three baseline protocols were expected because those protocols did not invoke the auditor. These missing values were excluded from classification metrics rather than treated as prediction errors. Similarly, a zero wasted-token value was interpreted according to the protocol's accounting definition. It did not establish that the final state was correct or that no computation had been ineffective.

### 3.2.3. Aggregation strategy

Records were grouped by protocol to calculate correctness rates and the mean, median and standard deviation of execution time and token usage. Further grouping by scenario and semantic ground truth exposed differences that would be hidden by overall averages. Auditor accuracy, precision, recall and F1-score were calculated from dependency-aware OCC executions with a recorded semantic prediction.

All executions were retained in the overall protocol comparisons, including completed executions with incorrect final values. A separate view of successful dependency-aware executions was used as a sensitivity check. Descriptive comparisons were used; no claim of statistical significance was made. The ten repetitions of a scenario measured repeated behavior on the same task and were not treated as ten new scenario designs.

## 3.3. SYSTEM DESIGN AND EXPERIMENTAL METHODS

### 3.3.1. Prototype architecture and technologies

The current prototype used Python for the backend and experiment runner, MongoDB for shared resources and research records, and MCP over HTTP for tool-based resource access. Pydantic schemas constrained structured model outputs. Ollama supplied local model inference through the LangChain integration. NetworkX supported resource and execution dependency analysis. LangGraph and Deep Agents supported the workflow demonstration, while FastAPI and a Next.js frontend provided a separate interface for observing execution events.

The formal benchmark and the interactive demonstration used related research components but different orchestration paths. The formal benchmark used a Python runner and structured preparation and decision calls. The demonstration used the Phase 4 graph. Consequently, the 400-run benchmark evaluated the explicitly implemented two-worker recovery procedure; it did not establish performance for arbitrary LangGraph workflows or general graph-scheduled recovery.

### 3.3.2. Worker preparation and decision stages

Each benchmark worker separated task preparation from state-dependent decision-making. Preparation summarized the task and identified required information before shared state was read. Decision-making then combined the task, the preparation output and a resource snapshot.

The decision schema allowed either a write or a stop action. A write required a complete resource object with exactly the expected fields. A stop action normalized the proposed value to null. Separating these stages enabled the proposed protocol to preserve the preparation output when a stale resource invalidated only the later decision. A fresh decision could also stop without writing when a condition became false after B's update.

### 3.3.3. Structural conflict detection

OCC used a conditional MongoDB update that matched both the resource identifier and the worker's expected version. A successful update replaced the resource value and incremented its version atomically. If the expected version no longer matched, the update failed and the middleware recorded a conflict.

For example, when both workers read version 1 and B committed version 2, A's subsequent write with expected version 1 was rejected. This structural check identified outdated access without determining whether A's intended operation remained valid. Successful resource mutation and subsequent provenance inserts were separate operations in the current MongoDB middleware; the implementation should therefore not be described as providing one atomic transaction across all resource and audit records.

### 3.3.4. Semantic conflict classification

After a version conflict, the Semantic Auditor received A's task, the old state, the current state, A's attempted state, B's changed fields and A's intended changes. It returned a structured disruptive or non-disruptive classification, a confidence value, affected premises and a concise reason.

A conflict was defined as non-disruptive when A's exact intended result could be reused without recomputing its state-dependent decision. A conflict was disruptive when a changed premise required recalculation or reevaluation of a condition. This distinction depended on the operation's meaning. Different write fields could still be dependent if one field controlled a decision about another, while independent fixed assignments could permit safe reuse.

The auditor classification selected the recovery path in the formal benchmark. No confidence threshold or additional deterministic semantic validator was applied by that runner. Classification errors could therefore lead either to unnecessary re-execution or to reuse of an invalid stale decision.

### 3.3.5. Dependency representation and selective recovery

The project's dependency service represented resource versions and execution nodes in a directed graph. Read edges connected a resource version to the node that consumed it. Workflow edges connected dependent execution steps. Descendant traversal identified execution nodes affected by a stale read, while unrelated worker nodes could be preserved. The implemented Phase 4 graph used a small, explicitly defined worker topology.

In the formal benchmark, recovery followed the known two-worker structure directly. For a non-disruptive prediction, the runner copied the current resource and applied only A's intended top-level field changes. The rebased value was committed using the current version. This preserved B's unrelated changes without repeating A's model calls.

For a disruptive prediction, the runner retained A's preparation, read the latest resource and recomputed A's decision. A new write was performed only if the fresh decision required one. Worker B's completed branch was preserved. The benchmark's reported node counts were logical counts assigned by these execution paths, rather than counts obtained from a generic dependency-graph scheduler.

### 3.3.6. Baseline protocols

**Table 3.4: Protocol behavior under the controlled schedule**

| Protocol | Conflict handling | Work repeated after conflict |
| --- | --- | --- |
| Naive | Writes a complete resource without validating its read version | None |
| 2PL | Holds an application-level resource lock across read, decision and write | None under the evaluated schedule |
| Full OCC | Rejects a stale write and restarts Worker A | Preparation, read, decision and commit if needed |
| Dependency-aware OCC | Audits the stale decision, then rebases or selectively recomputes | No model rerun for rebase; fresh read and decision for disruption |

The label 2PL refers to the implemented pessimistic baseline for one resource. It should not be interpreted as an evaluation of general multi-resource database locking. Similarly, full restart in this study meant restarting the conflicting worker transaction, while preserving B's completed work; it did not restart both agents or the entire application.

### 3.3.7. Evaluation measures

Final-state correctness was the primary outcome. For a protocol with N executions, the correctness percentage was:

`Correctness (%) = 100 × number of executions matching the expected final resource / N.`

This was a scenario-specific oracle for the prescribed B-then-A task order, rather than a general proof of serializability. An execution could finish without an exception and still be incorrect. A final version of 2 could be correct when A's fresh decision stopped after B's update.

Execution time was measured using a monotonic performance counter. Benchmark resource initialization and its initial verification occurred outside the main protocol timing interval. Token usage included the recorded input and output usage of worker preparation, worker decisions and, where applicable, the auditor and recovery model calls. It measured model-token consumption rather than electricity use, monetary cost or GPU utilization.

Wasted tokens were defined as tokens assigned to discarded worker model calls. Full OCC discarded A's original preparation and decision usage. Dependency-aware OCC assigned only A's original decision usage to waste when its disruptive path ran; the rebase path assigned zero. Auditor overhead contributed to total tokens rather than wasted tokens. These definitions allowed the protocol to reduce recorded waste while increasing total token usage.

For a metric M, the percentage change from full OCC to dependency-aware OCC was calculated as:

`Change (%) = 100 × (M_dependency − M_OCC) / M_OCC.`

For wasted-token reduction, the numerator was reversed so that a positive percentage indicated a reduction. Auditor precision, recall and F1-score treated disruptive as the positive class. The classification confusion matrix was inspected alongside application correctness to distinguish unnecessary recovery from unsafe decision reuse.

### 3.3.8. Scope of the evaluation

The evaluation covered two workers, one small resource per execution, ten held-out task pairs and an intentionally imposed stale-write schedule. It did not vary worker population, graph size, conflict probability or distributed deployment conditions. The runner warmed the configured worker model before benchmarking, but the available export did not include detailed inference or device telemetry. These boundaries were retained when presenting the findings in Chapter 4.

### 4.3.3. Successful rebasing of independent updates

ND1 illustrated a successful non-disruptive recovery. The resource initially contained quantity 85, price 24 and description Everyday Item. A's task was to set the price to 27, while B changed the description to Seasonal Label. After B committed, A's original full-resource write would have restored the old description.

The auditor classified the conflict as non-disruptive. The runner applied A's intended price change to B's current resource, producing quantity 85, price 27 and description Seasonal Label. All ten repetitions were correct. A's state-dependent model decision was reused without a model rerun, while B's update was preserved.

### 4.3.4. Selective recomputation and valid stop decisions

D1 demonstrated successful recovery of an arithmetic dependency. A initially calculated an allocation of 12 units from quantity 85, while B changed quantity to 44. Reusing A's stale quantity of 73 would have violated the required task order. The auditor classified the conflict as disruptive, and A's fresh decision produced quantity 32 from 44 minus 12. All ten executions were correct, with three logical recovery nodes recorded: read, decision and commit.

D2, D3 and D5 demonstrated recovery in which the correct fresh action was to stop. B's update made A's original condition false. Dependency-aware OCC re-read the resource and recomputed the decision, then left B's version-2 resource unchanged. Each of these scenarios was correct in all ten repetitions and recorded two recovery nodes because no new commit was required. These outcomes confirmed that successful recovery could involve withholding an obsolete action.

### 4.3.5. Unnecessary recovery caused by a false positive

In ND2, A needed to set quantity to the fixed target 120 while B changed price to 19. The intended quantity did not depend on the price, so rebasing could preserve the decision. The auditor nevertheless classified all ten conflicts as disruptive.

The runner recomputed A's decision and still produced the correct final resource in every repetition. However, the scenario recorded a mean of 483.70 wasted tokens and three re-executed logical nodes per execution. The remaining four non-disruptive scenarios used rebasing and recorded zero wasted tokens. This false positive therefore reduced the potential benefit of semantic reuse without harming final-state correctness.

### 4.3.6. Incorrect reuse in the current-price reduction scenario

D4 exposed a limitation of the semantic classifier and the recovery policy. The initial price was 29. A's task was to reduce the current price by 8, so its stale decision proposed 21. B also set the price to 21. After B committed, correct execution of A's task required a new calculation: 21 minus 8, producing 13.

The auditor classified the conflict as non-disruptive in all ten repetitions. The runner reused A's stale price of 21, producing an incorrect final resource at version 3. The numerical agreement between B's price and A's stale proposed price did not satisfy A's operation on the current value.

The recorded evidence establishes the false-negative classification, the resulting rebase and the incorrect final price. It does not reveal the model's internal cause for the error. All ten dependency-aware correctness failures were accounted for by this one scenario. A successful version-checked commit therefore did not establish semantic correctness when the recovery path relied on an incorrect classification.

### 4.4.3. Effect of retaining incorrect executions

The primary summaries retained all 100 dependency-aware executions. Restricting that protocol to its 90 correct executions yielded mean latency of 15.06 s, mean total usage of 2,572.20 tokens and mean waste of 289.86 tokens. These values were higher than the corresponding all-execution means because the failed D4 trials skipped necessary recomputation.

This restricted summary is a sensitivity check rather than a replacement comparison, since it changes the scenario composition. It shows why low recovery activity alone cannot establish efficiency: avoiding computation that was required for correctness can make a failed execution appear inexpensive.

### 4.4.4. Comparison with the pessimistic baseline

The 2PL baseline achieved 100% correctness with mean latency of 10.59 s, mean total usage of 1,369.10 tokens and zero recorded recovery waste. It outperformed both optimistic protocols on these measures for the controlled workload, despite incurring measurable lock wait.

This result was obtained for two workers contending for one small resource under a deliberately forced conflict schedule. It provides a clear baseline finding for this experiment, while leaving the behavior of larger workloads, lower conflict rates and longer independent computation unmeasured. The results presented here do not establish that dependency-aware OCC was the fastest, lowest-token or most reliable protocol overall.

### 4.4.5. Demonstration evidence and result boundaries

The project also included a frontend demonstration of resource versions, worker activity, semantic classification, recovery and final-state verification. The existing build report recorded passing isolated integration checks for both recovery paths and browser checks using test-only persistence and model substitutes. It also recorded that full live-service acceptance was unverified in that validation environment. These observations were retained as demonstration evidence and were not added to the 400-run benchmark or treated as new live LLM results.

The benchmark findings establish successful rebasing for four independent-update scenarios, correct selective recovery for four disruptive scenarios, unnecessary recovery for one independent-update scenario and unsafe reuse for one arithmetic scenario. The experiment measured these outcomes with one reported model and hardware configuration. Broader generalization and interpretation belong in the report's discussion chapter.
